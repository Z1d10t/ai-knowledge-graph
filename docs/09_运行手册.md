本文给出从 285 篇论文 Markdown 到最终交付包的完整命令。所有命令在仓库根目录执行（PowerShell）。

## 1. 数据准备

| 数据 | 默认位置 | 说明 |
|---|---|---|
| 论文 Markdown | `../材料论文/全部_285篇/md` | 285 篇，文件名即 `paper_id` |
| v2 抽取结果 | `evaluation/full_v2/kg_output/` | `raw/`、`enriched/`、`summary.json` |
| v3 规范层 | `evaluation/full_v3_delivery/` | 交付版 |

如果只拿到交付 ZIP，解压后即可打开页面，不需要重跑抽取。

## 3. 抽取 285 篇

先确认输入数量：

```powershell
(Get-ChildItem "../材料论文/全部_285篇/md" -Filter *.md).Count    # 期望 285
```

干跑：

```powershell
python article/extract_corpus.py --config my-config.toml `
  --input-dir "../材料论文/全部_285篇/md" `
  --output-dir evaluation/full_v2/kg_output --dry-run
```

正式抽取（可断点续跑，已有输出默认跳过）：

```powershell
python article/extract_corpus.py --config my-config.toml `
  --input-dir "../材料论文/全部_285篇/md" `
  --output-dir evaluation/full_v2/kg_output `
  --profile materials --continue-on-error --retries 2
```

输出：

- `raw/<paper>.json`：LLM 原样三元组；
- `enriched/<paper>.json`：标准化 + 观测后的结果（v3 的输入）；
- `summary.json` / `summary.csv`：逐篇状态与计数。

耗时取决于端点与并发：285 篇、每篇约 10–30 个块，`concurrency=8` 通常数小时；缓存开启后重跑只补缺失块。

## 10. 常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| `LLMTruncatedError` | token 预算不足 | 提高 `max_tokens`（16000+）或减小 `chunk_size` |
| 401/403 | key 错误或未设置 | 检查 `api_key` / `DEEPSEEK_API_KEY` |
| 429/5xx | 限流 | 降低 `concurrency`，增加 `max_retries` |
| 某篇 `enriched` 缺失 | 该篇块失败 | 用 `retry_failed_chunks.py` 或 `--force` 单篇重跑 |
| 页面 404 | 路径/端口错 | 确认 `--directory` 指向包含 `index.html` 的目录 |
| 页面空白 | 用 `file://` 打开 | 必须走本地 HTTP，端口不要被占用 |
| 中文乱码 | 终端编码 | `$env:PYTHONIOENCODING="utf-8"`；CSV 用 `utf-8-sig` 读 |
| 校验哈希失败 | 包内文件被改动 | 重新导出或恢复原文件 |

## 11. 时间与成本提示

- 抽取是唯一需要 LLM 的步骤；规范化、导出、页面、校验都离线。
- 缓存目录 `.kg-cache` 会保存每次回复；重复运行同一输入不再计费。
- 断点续跑：`extract_corpus.py` 检测已有 `raw`/`enriched` 文件并跳过。
- 先用 `--limit 3` 跑通，再全量，避免配置错误放大成本。
